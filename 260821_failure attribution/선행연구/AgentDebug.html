Where LLM Agents Fail and How They Can Learn From Failures

저자: Kunlun Zhu 외 (UIUC, Stanford, AMD, OpenManus 등), 2025.09
링크: arXiv:2509.25370 · github.com/ulab-uiuc/AgentDebug (코드·데이터 공개)
이 분야에서의 위치: 단일 에이전트 + 스텝 수준 + 근본 원인이라는, 첫 연구 목표와 정확히 같은 설정의 대표 논문. 분류학·벤치마크·프레임워크 3종 세트.
실패의 일차 병목은 오류 전파다 — 하나의 근본 원인 오류가 하류로 번져 궤적 전체를 무너뜨린다. 그 최초 지점을 찾아 바로 거기서부터 교정 피드백과 함께 재실행하면, 실패를 성공으로 뒤집을 수 있다.

1한눈에 보기 — 문제의식

기존의 에이전트 실패 분석은 오류 유형을 나열하거나 정성적 사례를 제시하는 데서 멈춘다 — 실패를 근본 원인(root cause)까지 체계적으로 추적하는 메커니즘이 없고, 발견한 실패를 바탕으로 에이전트가 스스로를 고치게 하지도 못한다. 이 간극을 메우기 위해 저자들은 오류 분석을 모듈화한다: 각 롤아웃(rollout, 에이전트의 1회 전체 실행)을 메모리·반성·계획·행동의 4개 운영 모듈로 분해하고, 각 실패를 근원 모듈에 귀속시키는 것이다.

수백 개의 궤적에 대한 대규모 인간 분석에서 저자들이 도달한 핵심 통찰:

Key Insight. 오류 전파가 LLM 에이전트 신뢰성의 일차 병목이다. 초기 실수는 그 자리에 머무는 일이 드물다 — 후속 단계로 연쇄되어 추론을 왜곡하고, 오판을 누적시키며, 궁극적으로 궤적 전체를 탈선시킨다. — §2.1, Key Insight 박스 번역

이 문제는 장기 과제(long-horizon task)에서 특히 심각하다 — 초기 실수가 이후의 추론과 행동을 왜곡해 복구를 어렵게 만들기 때문이다. 기존 개선 연구(CoT, Tree-of-Thought, 자기 반성)는 추론 탐색 공간을 넓히는 데 집중해 왔지만, 궤적을 상호의존적 과정이 아니라 고립된 단계들의 나열로 취급한다는 한계를 공유한다. 여기서 논문의 중심 질문이 나온다: LLM 에이전트는 어떻게 실패로부터 자신을 정련할 수 있는가?

2핵심 기여

  1. 실패 분석과 AgentErrorTaxonomy — 다양한 벤치마크에서 실패 궤적을 분석해 오류 전파(초기 실수가 후기 실패로 연쇄)가 견고성의 핵심 병목임을 보이고, 계획·도구 사용·메모리·반성을 아우르는 통합 실패 분류학을 도출.
  2. AgentErrorBench — ALFWorld·GAIA·WebShop의 실패를 체계적으로 주석한 최초의 큐레이션 데이터셋. 각 궤적에 세밀한 오류 범주와 실행 가능한 피드백(actionable feedback)이 부착돼, 에이전트 디버깅 방법의 연구·벤치마킹·비교를 위한 표준 시험대를 제공.
  3. AgentDebug — 결정적 오류를 식별하고 실행 가능한 피드백을 제공하는 디버깅 프레임워크. 근본 원인 탐지 정확도에서 강한 베이스라인을 24%p 상회하고, 신체화 추론·웹 상호작용·의사결정 도메인 전반에서 과제 성공률을 상대 26%까지 개선.

3주요 내용 I — AgentErrorTaxonomy (오류 분류학)

ALFWorld·WebShop·GAIA에서 500개 이상의 실패 궤적을 수집해 상세 인간 분석을 수행한 결과가 분류학의 토대다. 분류학은 5개 모듈로 조직된다 — 넷은 에이전트의 핵심 연산(메모리·반성·계획·행동)을, 다섯째는 외부 도구·인프라에서 비롯되는 시스템 수준 오류를 담당한다. 이 모듈식 관점은 흔한 오류 유형의 나열을 넘어, 한 단계의 약점이 어떻게 다른 단계로 연쇄되는지를 명료화해 실패의 추적·진단에 원칙 있는 접근을 가능하게 한다.

모듈정의 (원문 §2.1 표 번역)
Memory정보의 회상·검색 오류(거짓 회상, 누락, 검색 실패)로 후속 추론을 왜곡
Reflection진행 상황 모니터링·결과 해석의 실패(진행 오판, 결과 오독)로 경로 수정을 차단
Planning논리적으로 부실하거나 실행 불가능한 전략(불가능 행동, 제약 무시, 일관성 없는 하위 목표)이 연쇄 실수로 이어짐
Action연산 실행의 실수(형식 오류 출력, 잘못된 파라미터, 인자 누락) — 눈에 잘 띄지만 상류 오류를 가리는 경우가 많음
System-level추론 바깥의 실패(도구 크래시, API 불일치, 스텝 한도 초과) — 시스템 견고성의 문제

세부 유형은 총 17개다: Memory(환각/거짓기억, 검색 실패, 과잉단순화·불완전 요약), Reflection(진행 오판, 결과 오독, 인과 오귀속, 환각), Planning(제약 무시, 불가능 행동, 비효율 계획), Action(형식 오류, 무효 행동, 계획-행동 불일치, 파라미터 오류), System(스텝 한도, 도구 실행 오류, LLM 한계, 환경 오류). 저자들은 이 분류학이 단순한 오류 카탈로그가 아니라 "실패가 어디서 발원해 어떻게 전파·상호작용하는지 이해하기 위한 인과적 렌즈"로 설계됐음을 강조한다.

4주요 내용 II — AgentErrorBench (벤치마크)

4.1 구축 과정

대표 궤적 200개를 선별했다: ALFWorld 100, WebShop 50, GAIA 50. NLP·LLM 에이전트 연구 경험이 있는 대학원생 전문 주석자 10명이 AgentErrorTaxonomy 스키마로 각 궤적을 라벨했다. 주석은 결정 단계(decision-step) 수준으로 진행돼 모든 행동·반성·계획이 검토되고 해당 오류 유형이 태그된다. 나아가 주석자들은 표면적 실수를 전부 표시하는 대신, 하류 오류 연쇄를 설명하는 최소 근본 원인 집합을 식별하도록 지시받았다. 이 근본 원인 중심 원칙은 상세 지침과 보정 예시로 강조됐고, 3라운드의 파일럿 주석을 통해 반복적으로 정제됐다.

일관성 확보 절차: 저자 피드백이 있는 훈련 단계 → 공유 서브셋에 대한 독립 이중 주석 → 불일치의 집단 판정. 이 과정에서 범주 정의가 여러 차례 명료화됐다(예: 메모리의 "검색 실패"와 계획의 "제약 무시"의 구별). 최종 프로토콜은 간결하되 인과적으로 유의미한 태그를 목표로 세밀도와 신뢰도의 균형을 맞췄으며, 주석자 간 일치도는 Cohen's κ = 0.55(모듈 기준)로 상당한(substantial) 일치 수준이다.

κ=0.55를 어떻게 읽을 것인가. 전문가 10명이 훈련·보정을 거치고도 "무엇이 근본 원인인가"에서 상당히 갈린다는 뜻이다. 이 벤치마크로 실험할 때 방법 간 2~3%p 차이는 정답 자체의 흔들림 범위일 수 있다 — 신뢰구간과 완화 지표(relaxed)를 함께 보고하는 것이 안전하다. (참고: Who&When도 같은 문제를 불확실률 17~26%로 보고했다.)

5주요 내용 III — AgentDebug (방법)

5.1 전제: 모듈식 에이전트 형식화 (§3.1)

에이전트는 환경과 단계열로 상호작용한다 — 각 단계에서 상태를 관찰하고 행동을 산출해 상태-행동 쌍의 궤적을 만든다. 각 행동은 네 개의 순차적 모듈을 거쳐 생성된다: 관련 과거 정보를 회상하는 Memory → 진행을 평가하고 피드백을 해석하는 Reflection → 다음 전략을 수립하는 Planning → 저수준 연산을 실행하는 Action. 오류는 어느 모듈에서든 발생할 수 있고, 이른 실수는 종종 후기 단계로 전파되어 더 큰 실패로 증폭된다. 이 모듈식 롤아웃 설계는 에이전트의 내부 결정 과정을 반영할 뿐 아니라, 인간 주석자가 오류를 특정 모듈에 정렬할 자연스러운 구조를 제공해 실패 진단을 더 투명하고 해석 가능하게 만든다.

5.2 3단계 파이프라인 (Algorithm 1)

입력: 실패 궤적 τ = {(s₁,a₁),…,(s_T,a_T)}, 분류학 E_AET, 결정적 오류 기준 C_crit, 최대 반복 I [Stage 1] 세밀 분석 모든 단계 t, 모든 모듈 m∈{mem,plan,refl,act}에 대해 eₜᵐ ← MapToAET(sₜ,aₜ,m,E_AET) // 모듈별 오류 유형 부여 [Stage 2] 결정적 오류 탐지 C ← {τ, {eₜᵐ}, E_AET, C_crit} 를 묶어 LLM에 전역 판정 (T*, M*, Z*, φ⁽⁰⁾) ← DetectCriticalErrors(C) t* ← min(T*) // 가장 이른 결정적 단계 [Stage 3] 반복 디버깅 k = 1…I: τ⁽ᵏ⁾ ← ReRollout(τ⁽ᵏ⁻¹⁾, t*, φ⁽ᵏ⁻¹⁾) // t*부터 재실행 성공 시 반환, 실패 시 φ⁽ᵏ⁾ ← UpdateFeedback(…) // 피드백 정제

Stage 1 (세밀 분석): 궤적의 각 단계를 4개 모듈로 분해하고, 각 모듈 출력을 분류학에 사상해 모듈별 오류 프로필을 만든다. 탐지 프롬프트는 모듈별 평가 기준을 연쇄로 강제한다 — 메모리는 현재 입력만으로, 반성은 입력+이번 단계 메모리 출력으로, 계획은 +반성 출력으로, 행동은 계획 출력 기준으로 평가하며, 출력은 {오류 유무, 유형, 증거, 근거}의 엄격한 JSON이다.

Stage 2 (결정적 오류 탐지): 전 단계·모듈의 오류 프로필과 분류학, 결정적 오류 기준을 하나의 맥락으로 묶어 LLM이 전역적으로 판정한다. 복수의 결정적 후보가 나오면 가장 이른 단계를 취한다. 프롬프트의 가드레일: 사전 정의된 심각도 가중치에 의존하지 말 것, 초기 탐색 단계(1~3)는 명백한 근본 오류가 아니면 결정적으로 찍지 말 것, 1단계에는 (이력이 없으므로) 메모리·반성 오류가 있을 수 없음, 시스템 오류도 진짜 원인일 수 있음.

재현 시 주의 — 본문과 알고리즘의 불일치. §3.2 본문은 Stage 2를 반사실 검사처럼 서술하지만, Algorithm 1의 주석은 명시적으로 "via LLM (no rollout/counterfactuals)"이다. 즉 실제 구현은 재실행 없이, 반사실적 기준("고치면 성공으로 바뀌었을 오류")을 프롬프트에 담아 LLM이 판정한다. 교정 행동을 실제로 대입·재실행하는 방식은 오히려 베이스라인(Brute Force)으로 분리돼 있다 — 그리고 아래에서 보듯 그 방식이 더 나쁘다.

Stage 3 (반복 디버깅): 식별된 결정적 오류에 대해 오류 유형과 실행 가능한 교정 지침을 담은 피드백을 생성하고, 에이전트는 그 피드백 하에 처음부터가 아니라 t*에서부터 궤적을 재실행한다. 여전히 실패하면 피드백을 더 구체적으로 정제하며 고정 예산(최대 5회) 안에서 반복한다. 이 설계는 계산 노력을 실패 지점에 집중시킨다.

6실험 설계

  • 실험 1 (탐지 정확도): AgentErrorBench 200건에서 결정적 오류의 (단계, 모듈, 유형)을 맞히는 능력 평가. 판정 모델 GPT-4.1, temperature 0. 지표는 엄격도 3단계 — Step Exact(S), Step+Module(S+M), All Correct(ALL). 베이스라인: Direct Prompting(구조 없는 직접 질의), Brute Force(1단계부터 순차로 교정 행동 대입·재실행해 성공을 뒤집는 첫 단계 탐색), Binary Search(중간점 탐침 분할정복).
  • 실험 2 (하류 디버깅): ALFWorld·GAIA·WebShop에서 실패 → 성공 전환율. 에이전트 백본 3종(GPT-4o-mini, Qwen3-8B, Qwen3-Next-80B), 결정적 단계에서 시작하는 재실행 최대 N=5회. 베이스라인: Self-Refine(명시적 인과 진단 없는 반복 수정), Vanilla Debugger(결정적 오류 분류 없는 소박한 사후 교정), Tree-of-Thought, Best-of-N. 공정성을 위해 모든 베이스라인의 최대 시도 수를 총 토큰 사용량 기준으로 AgentDebug에 맞춰, 관측된 이득이 자원 증가가 아닌 표적 오류 복구에서 왔음을 보장.
  • 실험 3 (절제): 재시도 횟수, 판정 모델 교체, 롤아웃 형식의 3축.

7.4 오류 전파 분석 (§5.2, Figure 8)

10개 과제의 히트맵에서 초기 실수가 후속 단계로 연쇄되며 점점 짙어지는(심각도가 누적되는) 양상이 확인된다. 전파의 가능성과 길이는 모듈에 따라 크게 다르다: 메모리·반성 오류가 가장 흔한 전파원으로 대개 초·중반(약 5~15단계)에 발생한다 — 한번 사실을 잘못 기억하거나 진행을 오판하면 이후 계획이 체계적으로 왜곡되어 잘못된 행동 선택의 반복 사이클로 이어진다. 계획 오류도 크게 기여하며(제약 무시·실행 불가능 전략이 실행을 시도할수록 누적), 행동 수준 오류는 더 가시적이고 때로 복구 가능하지만 형식 오류·파라미터 누락은 여전히 실행을 탈선시킬 수 있다. 시스템 수준 문제(도구 크래시, 스텝 한도 소진)는 연쇄가 아니라 즉각적 종료점으로 작동한다.

두 가지 설계 교훈이 도출된다: 첫째, 조기 탐지·교정이 결정적이다 — 연쇄가 시작되면 되돌리기 어렵다. 둘째, 메모리 검색과 반성을 강화하는 메커니즘(외부 메모리, 진행 추적, 검증 프롬프트)이 전파 위험을 실질적으로 줄일 수 있다.

8한계와 시사점

  • 규모·도메인 — 3개 환경 200건은 표준 시험대로서의 첫걸음이지 대표 표본이 아니다.
  • 프롬프트 기반의 상한 — 전용 디버깅 모델 학습 대신 저비용 프롬프트 워크플로를 택했으므로, 완전 학습된 특화 모델(예: AgenTracer류)보다 낮을 수 있다.
  • 시사점 (첫 연구 관점) — ① 궤적을 모듈 태그가 강제된 형식으로 수집하면 주석·진단이 쉬워진다(부록 프롬프트 재사용 가능). ② 정의는 "17유형(관찰) × 최소 근본 원인 집합(반사실)"의 2층 구조를 표준으로. ③ Step 45%(절반 이상 오답), Brute Force 역설, 판정 모델 병목 — 열린 틈이 많다. 윈도우 증강의 "후보 → 국소 재식별" 패턴을 이 벤치마크에 이식하는 것이 자연스러운 다음 실험.
