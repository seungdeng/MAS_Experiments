TRAIL: Trace Reasoning and Agentic Issue Localization

궤적 추론과 에이전트 이슈 위치 특정 — 관찰자 관점의 분류학과 스팬 수준 벤치마크
저자: Darshan Deshpande, Varun Gangal, Hersh Mehta, Jitin Krishnan, Anand Kannappan, Rebecca Qian (Patronus AI)
발표: 2025 (v3: 2025.06) · arXiv:2505.08638 · HuggingFace 데이터 공개
이 분야에서의 위치: 산업(관측 도구 회사)에서 나온 벤치마크. OpenTelemetry 스팬 형식 채택으로 학술-산업을 잇고, "최고 모델 11%"라는 난이도 기준선을 세움.
에이전트 워크플로 트레이스의 평가·디버깅은 수작업 분석에 의존하고 있으며 규모를 감당하지 못한다. 형식적 오류 분류학과 인간 주석 트레이스 148건(오류 841개)을 제시한다 — 최신 장문맥 LLM조차 이 데이터에서 최고 11%에 그친다.

1한눈에 보기 — 문제의식

에이전트 워크플로가 다양한 도메인으로 확산되면서, 이들이 생성하는 복잡한 트레이스를 확장 가능하고 체계적으로 평가할 필요가 절실해졌다. 현재의 평가는 길고 긴 워크플로 트레이스에 대한 수작업·도메인 특화 인간 분석에 의존하는데, 이는 에이전트 출력의 복잡성과 양이 늘어나는 속도를 따라가지 못한다. 이 환경의 오류 분석은 외부 도구 출력과 언어모델 추론의 상호작용 때문에 더 복잡해서, 전통적 소프트웨어 디버깅보다 어렵다.

또 하나의 배경은 LLM-as-a-judge의 한계다. LLM 판사는 여러 평가 영역에서 성과를 냈지만, 편향 전파와 긴 입력에 대한 강건성 부족이 알려져 있고, 트레이스 평가는 긴 맥락 위에서의 견고한 추론을 요구하기 때문에 이 영역에서는 아직 널리 적용되지 못했다. 그래서 저자들은 (1) 에이전트 워크플로 트레이스를 위한 견고하고 동적인 평가 방법의 필요를 논증하고, (2) 에이전트 시스템에서 마주치는 오류 유형의 형식적 분류학을 도입하며, (3) 이 분류학에 기반해 실제 벤치마크에 접지된 인간 주석 트레이스 148건(TRAIL)을 제시한다. 생태적 타당성(ecological validity)을 위해 트레이스는 단일·다중 에이전트 시스템 모두에서, 소프트웨어 엔지니어링과 오픈월드 정보 검색이라는 실전 응용을 중심으로 큐레이션됐다.

해설 AgentDebug와의 관점 차이. AgentDebug의 분류학이 에이전트 내부(어느 모듈의 잘못인가)를 보는 아키텍처 관점이라면, TRAIL은 트레이스를 밖에서 읽는 관찰자 관점이다 — 실행 기록에 나타난 이슈를 추론/시스템/계획·조정으로 나눈다. 같은 실패도 두 분류학에서 다른 이름을 갖게 되며, 이 미사상(未寫像)이 분야의 공백 중 하나다.

2핵심 기여

  1. TRAIL 분류학 — 에이전트 시스템의 오류를 3대분류(추론 / 시스템 실행 / 계획·조정) 아래 세밀하게 조직한 형식 분류 체계.
  2. TRAIL 데이터셋 — GAIA(오픈월드 정보 검색)·SWE-bench(소프트웨어 엔지니어링) 기반의 대형 인간 주석 트레이스 148건, 고유 오류 841개. OpenTelemetry 표준 형식으로 수집돼 실제 관측 소프트웨어와 호환.
  3. 난이도의 실증 — 최신 장문맥 LLM들이 트레이스 디버깅에서 형편없이 수행함을 확인: 최고 Gemini-2.5-Pro가 TRAIL 전체에서 겨우 11%(joint accuracy). 8개 모델 중 3개는 전체 맥락을 처리조차 못 한다.

4주요 내용 II — 데이터셋 구축

4.1 트레이스 생성 — 두 개의 실전 무대

  • GAIA (오픈월드 정보 검색): 표준 계층 오케스트레이션 구조를 따라 Hugging Face의 OpenDeepResearch 에이전트로 트레이스 생성. 매니저와 검색 에이전트의 백본으로 당시 SOTA인 o3-mini-2025-01-31을 배정(강한 도구 사용·계획 능력 근거). 매니저 에이전트가 Visualizer·TextInspector 도구를, 검색 에이전트가 구글 검색·페이지 방문·아카이브 검색 등 8종 도구를 가진 구조(부록 Figure 7).
  • SWE-bench (소프트웨어 엔지니어링): 단일 에이전트의 계획 오류와 맥락 처리 오류를 끌어내기 위해 CodeAct 에이전트를 사용 — 샌드박스 환경에서 파이썬 인터프리터와 gitingest 라이브러리에 접근. 백본은 SW 엔지니어링 성능이 강한 claude-3-7-sonnet-20250219. 나아가 오류를 유기적으로(organically) 유도하기 위해 출력 길이 제한, 탐색 강제 같은 지시적 제약을 프롬프트에 추가했다.
해설 "유기적 유도"의 위치. 오류를 인위 주입(injection)한 것이 아니라, 제약을 걸어 에이전트가 자연스럽게 실수하기 쉬운 조건을 만든 것이다 — 합성 주입(Aegis류)과 순수 자연 실패의 중간쯤에 있는 데이터 확보 전략으로, 레이블은 여전히 사람이 단다.

4.2 형식 — OpenTelemetry 스팬

실전 트레이싱·관측 소프트웨어와의 호환성을 위해 모든 트레이스는 OpenTelemetry, 구체적으로 에이전트 호환 오픈소스 파생 표준인 openinference 형식으로 수집됐다. 트레이스는 스팬(span)들의 트리다 — 각 스팬은 timestamp, trace_id, span_id, parent_span_id, span_name(예: LLM 호출), 그리고 입력 메시지·모델명·토큰 수·출력 등을 담은 속성(attributes)으로 구성된다(Figure 2). 오류 주석은 스팬 ID를 위치로 참조한다.

// 스팬 구조 요지 (Figure 2 재구성) { timestamp, trace_id, span_id, parent_span_id, span_name: "LiteLLMModel.__call__", span_kind: "Internal", attributes: { input.messages, llm.model_name, llm.token_count.{prompt,completion,total}, output.value, ... } } // 오류 주석 예 { category: "Instruction Non-compliance", location: "61c56...", evidence: "...", description: "모델이 최종 답을 직접 패치로 제출하지 않고 저장소 정보만 제공", impact: "HIGH" }

4.3 주석과 검증

소프트웨어 엔지니어링·로그 디버깅 전문성을 가진 주석자 4명이 트레이스를 라벨했다. 일치도 평가를 위해 별도의 63개 트레이스가 배정됐고, 큐레이션 기간 중 높은 주석자 간 일치가 확인됐다(세부 절차·수치는 부록 A.7).

주석 후 검토 기준 오류는 GAIA 114개·SWE-bench 30개 트레이스에서 발견됐다. 분포의 특징: 출력 생성 오류가 압도적이다 — 형식 오류와 지시 불이행만으로 전체 841개 중 353개, 약 42%. 반면 시스템 실행 오류는 드물다. 이 범주 불균형은 두 가지를 시사한다. 첫째, 출력 생성 오류의 만연은 신중한 프롬프트 엔지니어링에도 불구하고 현재 LLM 시스템이 고수준 추론과 과제 파라미터 이해에 어려움을 겪는다는 것. 둘째, API 실패 같은 오류는 드물지만 재앙적일 수 있고 복구가 어려워 탐지가 결정적이라는 것 — 드물지만 중대한 유형을 포함하는 분류 체계의 필요가 여기서 나온다. 영향도 분포는 Medium 363(43.2%) > High 304(36.1%) > Low 174(20.7%)이며, 출력 생성 오류의 약 44%는 저영향이다.

4.5 맥락 길이 — 이 데이터의 구조적 난관

트레이스 JSON을 그대로 입력하면 맥락이 얼마나 긴가(Table 2): GAIA는 평균 286.85K 토큰, 최대 7.50M(gpt-4.1 토크나이저 기준). SWE-bench는 평균 616.92K~727.75K, 최대 2.05M~2.43M. 즉 분포의 상당 부분이 최신 모델의 최대 입력 한도(200K~1M)를 초과하고, 평균조차 컨텍스트 창의 상당 비율을 채운다(Figure 5). 8개 평가 모델 중 3개는 전체 맥락을 처리할 수 없었다.

이 표가 말하는 것. 트레이스 평가의 병목이 추론력 이전에 입력 수용력에 있다는 실증이다. "긴 궤적을 어떻게 잘라 보여줄 것인가"(압축·가지치기·윈도우)가 왜 이 분야의 중심 설계 변수인지가 이 수치들에서 나온다.

5실험 설계

  • 과제: 트레이스(JSON)를 입력으로 주고, 오류의 위치(스팬)·범주·영향도를 예측하게 한다.
  • 지표: 범주 F1(Categorical F1), 위치 정확도(Location Accuracy), 그리고 위치+범주를 모두 맞혀야 하는 Joint Accuracy.
  • 평가 모델: 장문맥 SOTA 8종 — GPT-4.1, o1, o3, Claude-3.7-Sonnet, Llama-4-Maverick/Scout, Gemini-2.5-Pro/Flash.

6실험 결과

6.1 주 결과 — 최고가 11%

현대의 장문맥 LLM들은 트레이스 디버깅에서 형편없이 수행한다: 최고인 Gemini-2.5-Pro가 TRAIL 전체에서 겨우 11%(joint). 데이터별로는 GAIA 18%, SWE-bench 5%다. 8개 중 3개 모델은 전체 맥락을 처리하지 못했다. 결론부의 진단: 이 결과는 에이전트 시스템 고유의 복잡성과 LLM의 맥락 한계로 인해, 기존 모델이 복잡한 에이전트 트레이스를 체계적으로 평가하는 데 실패함을 보여주며, 확장 가능하고 체계적인 에이전트 워크플로 평가를 위한 새 프레임워크가 필요하다.

6.3 범주별 성능 (Figure 4)

  • 예측이 어려운 범주: 맥락 처리 실패(Context Handling Failures)는 거의 모든 모델이 F1 ≈ 0.00 — 고급 추론을 요구한다는 뜻이며 유일한 예외가 Claude-3.7-Sonnet(0.18). 도구 선택 오류도 어렵다(대부분 0.00~0.08, 예외적으로 o3 0.53, Claude-3.7 0.27, Gemini-2.5-Pro 0.26). 과제 오케스트레이션도 전반적으로 낮다(0.00~0.08, Gemini-2.5-Flash만 0.47).
  • 모델 간 성능이 갈리는 범주: 목표 이탈은 Gemini 계열이 최고(Pro 0.70, Flash 0.41)인 반면 Claude·o3는 중간(0.31, 0.24), o1 등 비추론 모델은 최저(≤0.05). 빈약한 정보 검색도 Gemini 둘이 유독 좋다(0.50, 0.53; 나머지 <0.30) — 맥락 관련 실패의 진단에 강하다는 시사.
  • 의외의 패턴: 언어 전용 환각은 모든 모델이 비교적 잘 잡는다(0.14~0.59) — 고급 추론 없이도 예측이 쉬운 편. 형식 오류는 비단조적이다: GPT-4.1(0.43)과 Gemini-2.5(0.44~0.57)가 좋고, o1·o3·Claude-3.7이 오히려 나쁘다(0.23~0.31) — 더 오래됐거나 비추론 모델인 o1·GPT-4.1이 o3를 이기는 범주라는 점이 눈에 띈다.

7한계와 시사점

  • 규모와 편중 — 148 트레이스, 2개 도메인. SWE-bench 쪽은 31건으로 특히 작다. 오류 분포도 출력 생성에 쏠려 있어(42%), 드문 범주의 평가는 표본이 얇다.
  • 단일 시점 생성 — 특정 에이전트 구성(o3-mini 오케스트레이션, CodeAct+Claude-3.7)의 실패 분포이므로, 다른 스택에서는 분포가 다를 수 있다.
  • 시사점 (첫 연구 관점) — ① OTel/openinference 스팬 형식을 익히는 교재로 최적: 이 데이터를 로드해 길이·오류 위치·유형 분포를 재현하는 것이 웜업 과제다. ② "최고 11%, 길이와 음의 상관"이라는 기준선은 어떤 새 방법이든 기여할 공간이 크다는 뜻. ③ 스팬 수준 위치 + 범주 + 영향도라는 3요소 주석 설계는 자체 데이터를 만들 때의 참조 템플릿이다.
